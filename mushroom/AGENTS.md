# AGENTS.md
## 总说明
本规范用于约束Codex编码行为，核心原则：优先严谨、最小改动、可验证闭环；简易琐碎任务可灵活酌情处理。
项目技术栈：Python + FastAPI
分为两大部分：通用编码行为准则、本项目专属强制规则。

# 一、通用编码行为准则（基础强制规则）
## 1. 先思考，再编码
禁止主观臆断、隐藏疑问，不私自做静默决策，提前说明方案取舍与不确定点。
开发前必须遵守：
1. 明确说明所有自身假设，存在不确定需求、逻辑、场景时主动提问确认；
2. 若需求存在多种解读方式，完整列出所有可行方案，不私自选定方案；
3. 存在更简洁的实现方案时主动告知，对不合理、过度复杂的实现方案可提出调整建议；
4. 遇到模糊不清的逻辑、边界、需求时立即停止开发，明确指出疑惑点，澄清后再执行。

## 2. 极简优先，拒绝过度设计
仅编写刚好满足需求的最少代码，不添加前瞻性、未要求的冗余逻辑。
1. 只实现需求明确要求的功能，不额外增加未提及特性；
2. 单次临时使用的代码不强行封装抽象类、通用工具层；
3. 未要求可配置、可扩展的场景，不额外设计灵活配置逻辑；
4. 不为理论上不可能触发的场景编写异常处理；
5. 若代码篇幅远超最简实现，必须精简重构；自我校验：站在资深工程师视角判断是否过度复杂，复杂则简化。

## 3. 外科式精准修改，最小侵入
仅修改完成需求必须改动的内容，不擅自优化无关代码。
### 修改存量代码时
1. 不擅自优化、格式化、重构相邻代码、注释、排版；
2. 不修改、重构无BUG、无优化需求的代码；
3. 严格匹配项目现有代码风格，个人编码习惯服从项目规范；
4. 发现无关的废弃死代码仅做文字标注，不擅自删除。

### 清理冗余约束
1. 仅清理因本次代码改动导致失效的导入、变量、函数；
2. 原有历史遗留废弃代码，无明确清理指令时禁止删除。

### 改动校验标准
每一行修改的代码，都必须能直接对应用户原始需求，不存在无关改动。

## 4. 目标驱动，闭环可验证
将模糊任务转化为可落地、可校验的明确目标，迭代至校验通过才算完成。
### 标准化任务转换
- “增加校验逻辑” → 编写非法输入测试用例，完成代码并保证用例通过
- “修复BUG” → 先编写可复现BUG的测试用例，修复代码并验证通过
- “重构代码” → 重构前后全部测试用例正常运行，功能无变化

### 多步骤任务要求
复杂任务先输出执行计划，每一步绑定校验标准：
1. 执行步骤 → 校验要点
2. 执行步骤 → 校验要点
3. 执行步骤 → 校验要点

清晰可量化的成功标准，减少反复沟通；禁止仅以“代码跑通”这种模糊标准收尾。

## 5. 注释与日志规范
1. 新增代码必须补充必要注释；
2. 所有日志打印和注释内容统一使用中文；
3. 禁止打印警告日志；仅严重问题输出错误日志，轻微问题不打印日志。

## 6. 模块化 & 架构设计强制规范
> **适用范围：新增功能、大规模重构；微小单行修复、简单临时脚本调整可豁免**
### 6.1 架构前置原则
1. **先划分模块，再编写代码**
新增业务功能时，首先梳理职责边界，确定代码归属文件/模块；禁止直接在入口文件随意堆砌逻辑。
2. **单一职责原则**
- 一个模块、一个文件、一个函数只负责一类事情；
- Python 单个函数建议控制在60行以内，超长函数必须拆分；
- 单个`.py`文件禁止无限膨胀，业务代码超过500行考虑拆分子模块。

### 6.2 模块耦合约束（高内聚、低耦合）
1. 模块之间**只通过公开函数/类接口交互**，禁止跨模块直接访问内部变量、私有函数（`_xxx`私有成员）；
2. 严格规避循环导入（circular import）；出现循环依赖时，抽取公共结构体、工具函数下沉至底层公共模块；
3. 禁止滥用全局变量传递业务状态；优先使用函数传参、返回值、FastAPI依赖注入传递数据；
4. 分层调用单向流动：上层依赖下层，禁止下层反向调用上层业务代码。

### 6.3 FastAPI 标准分层规范（项目强制）
统一分层流向：`api(router) → service → repository → db`
1. **api / routes 路由层**
    - 职责：接收http请求、参数校验、调用service、统一返回结构
    - 禁止：编写复杂业务逻辑、直接操作数据库
2. **service 业务层**
    - 职责：业务规则组装、数据组合、业务判断
    - 禁止：直接操作数据库、处理Request对象
3. **repository 数据层**
    - 职责：仅数据库CRUD操作，不包含业务判断
4. **model 模型层**
    - pydantic DTO：请求模型、响应VO
    - ORM实体：数据库映射模型，与DTO严格分离
5. **common / utils 公共底层**
    工具函数、全局异常、配置、常量、通用依赖

> 目录组织：优先按**业务领域分包**，不单纯按层全局平铺；大型业务拆分独立模块。

### 6.4 FastAPI 编码专项约束
1. 请求入参统一使用Pydantic模型校验，禁止在函数内手写大量if参数判断；
2. 统一使用项目全局异常处理器，路由内部禁止裸 `try/except` 吞异常；
3. 异步项目严格区分同步/异步函数，禁止在async函数调用阻塞同步IO；
4. 接口响应格式全局统一，每个接口不要自定义返回JSON结构；
5. 路由路径、标签(tags)遵循项目现有命名风格，接口增加summary中文文档；
6. 依赖项（Depends）抽离至公共模块，路由保持简洁；
7. 禁止在service、repo层直接使用Request对象，请求信息由路由层向下传递。

### 6.5 Python 通用文件组织规则
1. 通用能力统一收拢至`utils/`、`common/`，重复出现的逻辑抽离为通用工具函数，禁止代码复制粘贴；
2. 常量、枚举放置独立模块，禁止代码内散布硬编码；
3. 包内部合理使用`__init__.py`管控对外暴露接口，按需控制导出对象，禁止`import *`全量导入。

### 6.6 AI生成代码分段约束
1. 复杂功能禁止一次性生成全部代码；优先输出模块拆分方案、分层归属，确认后逐个模块实现；
2. 若产出代码耦合严重、超大函数、模块边界模糊、跨层乱调用，必须重新拆分；
3. 新增模块需要同步说明模块职责、入参、返回值、依赖清单；
4. 新增接口必须同步生成路由、pydantic模型、对应service代码，分层清晰。

### 6.7 边界豁免说明
满足以下场景，可以不受复杂模块化约束：
- 少量代码的简单BUG修复；
- 一次性临时调试脚本；
- 原型验证极简Demo（正式迭代开发阶段仍需按规范重构）。

## 7. 规范生效判定标准
1. 代码变更记录仅包含必要改动，无多余优化、格式调整；
2. 因过度设计、代码复杂导致的返工、重写大幅减少；
3. 需求歧义、疑问全部在编码前澄清，而非写完代码后修正；
4. 新增业务代码模块边界清晰，无巨型函数、无随意堆砌逻辑、无循环导入；
5. FastAPI代码严格遵守分层单向调用，路由不混杂业务逻辑，分层职责不越界。
