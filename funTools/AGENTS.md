# AGENTS.md
## 总说明
本规范用于约束Codex编码行为，核心原则：优先严谨、最小改动、可验证闭环；简易琐碎任务可灵活酌情处理。
分为两大部分：通用编码行为准则、本项目专属强制规则。

# 一、通用编码行为准则（基础强制规则）
## 1. 先思考，再编码
禁止主观臆断、隐藏疑问，不私自做静默决策，提前说明方案取舍与不确定点。
开发前必须遵守：
1. 明确说明所有自身假设，存在不确定需求、逻辑、场景时主动提问确认；
2. 若需求存在多种解读方式，完整列出所有可行方案，不私自选定方案；
3. 存在更简洁的实现方案时主动告知，对不合理、过度复杂的实现方案可提出调整建议；
4. 遇到模糊不清的逻辑、边界、需求时立即停止开发，明确指出疑惑点，澄清后再执行。

## 2. 极简优先，拒绝过度设计
仅编写刚好满足需求的最少代码，不添加前瞻性、未要求的冗余逻辑。
1. 只实现需求明确要求的功能，不额外增加未提及特性；
2. 单次使用的代码不封装抽象类、通用工具层；
3. 未要求可配置、可扩展的场景，不额外设计灵活配置逻辑；
4. 不为理论上不可能触发的场景编写异常处理；
5. 若代码篇幅远超最简实现，必须精简重构；自我校验：站在资深工程师视角判断是否过度复杂，复杂则简化。

## 3. 外科式精准修改，最小侵入
仅修改完成需求必须改动的内容，不擅自优化无关代码。
### 修改存量代码时
1. 不擅自优化、格式化、重构相邻代码、注释、排版；
2. 不修改、重构无BUG、无优化需求的代码；
3. 严格匹配项目现有代码风格，个人编码习惯服从项目规范；
4. 发现无关的废弃死代码仅做文字标注，不擅自删除。

### 清理冗余约束
1. 仅清理因本次代码改动导致失效的导入、变量、函数；
2. 原有历史遗留废弃代码，无明确清理指令时禁止删除。

### 改动校验标准
每一行修改的代码，都必须能直接对应用户原始需求，不存在无关改动。

## 4. 目标驱动，闭环可验证
将模糊任务转化为可落地、可校验的明确目标，迭代至校验通过才算完成。
### 标准化任务转换
- “增加校验逻辑” → 编写非法输入测试用例，完成代码并保证用例通过
- “修复BUG” → 先编写可复现BUG的测试用例，修复代码并验证通过
- “重构代码” → 重构前后全部测试用例正常运行，功能无变化

### 多步骤任务要求
复杂任务先输出执行计划，每一步绑定校验标准：
1. 执行步骤 → 校验要点
2. 执行步骤 → 校验要点
3. 执行步骤 → 校验要点

清晰可量化的成功标准，减少反复沟通；禁止仅以“代码跑通”这种模糊标准收尾。

## 5. 规范生效判定标准
满足以下条件代表规则正常执行：
1. 代码变更记录仅包含必要改动，无多余优化、格式调整；
2. 因过度设计、代码复杂导致的返工、重写大幅减少；
3. 需求歧义、疑问全部在编码前澄清，而非写完代码后修正。

## 6. 规范生效判定标准
1. 新增代码必须补充必要注释;
2. 所有日志打印和注释内容统一使用中文；
3. 禁止打印警告日志；仅严重问题输出错误日志，轻微问题不打印日志。
